# Architecture

> and the reward, which are current. It was written across many phases and still

> `ReplicaWorker`), the lock-based oracle (`oracle.py`, `OracleCoordinator`), the

This document explains how the system works, from the simulator up to the learning algorithm. It is meant to be readable without digging through the code first.

## The problem

A swarm of identical robots starts scattered on a plane. Each robot can move and can broadcast a short message over short-range infrared, which only nearby robots receive. There is no central controller and no global position sense. Given a target shape, supplied as a small image, the swarm should rearrange itself so that the robots cover that shape.

Because every robot is identical and only sees its own neighborhood, the goal is a single shared policy that, run independently on every robot, produces collective shape assembly.

## The simulator (Unity)

Unity does the physics and the communication, and nothing about the learning. It runs headless during training.

A scene contains one or more arenas. Each arena holds a swarm, a seed robot that gives the swarm a shared reference point, and a target shape. `SceneBootstrap.cs` spawns the requested number of arenas at startup, reading `KILOBOT_NUM_ARENAS` from the environment so the same build can run different arena counts. Running several arenas inside one Unity instance amortizes the simulator startup cost and gives more rollout data per step.

Each robot is a small agent (`KilobotAgent.cs`) with simple differential movement (`KilobotMovement.cs`). On each decision it reports what it can sense, including the messages from neighbors it has heard, and it receives an action: two motor values and a message to broadcast. Infrared messaging is modeled by range, so a robot only hears robots close to it.

Two pieces connect the simulator to Python. The first is the ML-Agents communicator, which carries observations and actions. The second is a custom side channel (`CriticChannel.cs`) that, every step, sends Python the full interaction graph of each arena: the nodes (robots, with their features) and the edges (which robots are within communication range). That graph is privileged information used only to train the critic, and it never reaches the robots.

`StepDriver.cs` and `HeartbeatAgent.cs` keep the stepping cadence regular, and `ImageLibrary.cs` loads the target images that define each arena's shape.

## Centralized training, decentralized execution

The method is MAPPO, a multi-agent form of PPO, set up in the centralized-training, decentralized-execution style.

Decentralized execution means the thing a robot runs is a policy that takes only local information: the robot's own state, the seed reference, and a summary of the messages it has heard. Every robot runs the same policy. This is the actor, and it is the only part kept for deployment.

Centralized training means that while learning, an additional model is allowed to see everything in an arena at once: all robots and all of their connections, as a graph. This is the critic. It estimates how good a situation is, which makes the learning signal far less noisy than it would be from local views alone. The critic is a training aid and is thrown away afterward.

## The actor

The actor is a set-based network (a DeepSet style aggregator). A robot has heard messages from a varying number of neighbors, so the network has to accept a variable-size set and be invariant to the order it arrives in. It embeds each remembered neighbor message, pools those embeddings into a fixed-size summary, combines that with the robot's own state and the seed reference and the target latent, and outputs an action.

Each robot keeps a small database of the most recent messages it has heard, up to a fixed capacity. That database is the memory the actor reads from, so a robot can act on neighbor information from slightly earlier even if no one is broadcasting at the exact moment it decides.

The action has two parts: the motor command that moves the robot, and the message it will broadcast to its neighbors on this step. The message is part of the action because what a robot chooses to say is part of the learned coordination behavior.

The actor emits an unbounded mean; the action is sampled from a Gaussian around it and then squashed into range with `tanh` (messages into [-1, 1], motors into [0, 1]), in the style used by SAC. The policy's log-probability accounts for the squash, so the density is correct in the bounded space. The important property is that the buffer stores the pre-squash sample and the simulator executes the squash of exactly that sample, so the action that is executed and the action whose log-probability the policy gradient optimizes are the same. An earlier version instead clamped the action after storing the unclamped sample, which silently decoupled the two; see `docs/tuning.md`.

### A recurrent alternative to the DeepSet actor

The set-based actor pools the remembered messages into a permutation-invariant sum, and the motor command is read from that sum. That pooling turned out to make it hard for the motors to become a function of the navigation direction: the direction has to survive being summed together with a variable number of neighbor messages before it reaches the wheels, and the policy tends to settle on a constant motor output instead. The investigation behind this conclusion is in `docs/tuning.md`.

The alternative actor (`KILOBOT_ACTOR=gru`) replaces the DeepSet-plus-database aggregator with a per-robot recurrent cell (a GRU). Instead of pooling a set each tick, each robot carries a hidden state that is updated one message at a time, giving the direction a direct route into the motor output. Two inputs are made explicit in this design. The seed reference is a distinct typed input rather than being mixed into the pooled message set. And the robot is given a short proprioception vector: dead-reckoned odometry computed from its own last motor command and how long it held it: path length, straight-line displacement, the sine and cosine of the heading change, the elapsed time of the interval, and the cumulative distance travelled so far this episode. The elapsed time and cumulative distance are carried as their own channels rather than folded into displacement, so a stationary robot still registers that time passed, and the one-step recurrent cell does not have to integrate a running odometer it has no gradient path to build. In this first version the hidden state is carried across ticks but stored detached, so the gradient flows through a single cell step and not through time; this keeps the change confined to the aggregator. The DeepSet actor remains the default and both share the same squashed-Gaussian action.

### An event-driven, split-observation actor

A third actor (`KILOBOT_ACTOR=gru_split_observation`) treats each decision as a single event: the robot has received exactly one transmission since its last decision, from a neighbor, a corner seed, a center seed, or a wall seed, never more than one -- true of the underlying hardware (one IR receiver, one signal per tick, regardless of which of the four broadcasts it) and, since phase 10 (`docs/tuning.md`), true of the simulation as well. That transmission fills a twenty-two-value vector `Tc`: the first nine entries are the neighbor message if the event came from a neighbor (zero otherwise), the tenth is that message's received signal strength (the robot's only ranging measurement of the sender, without which neighbor events carry no geometric grounding at all), the next four are the corner-seed one-hot-times-strength if the event came from a corner seed (zero otherwise, and at most one of the four nonzero even then), the next four are the center-cluster per-direction strength if the event came from a center seed (zero otherwise, and at most one of the four nonzero even then; phase 11, see "Wall and center seeds" below), and the last four are the wall-seed per-side strength if the event came from a wall seed (zero otherwise, and at most one of the four nonzero even then). On a tick where a robot is simultaneously in range of more than one individual sender -- another kilobot, a corner-seed kilobot, a center-seed kilobot, or a wall-seed kilobot on any of up to two adjacent sides -- which single one becomes the event is decided by sampling from one flat pool holding every individual sender together (every neighbor row, every corner slot, every center slot, every wall side, not the four categories as combined buckets), weighted by signal strength, with no priority given to any kind. A tick with nothing available at all does not produce a decision: Unity requests a decision only when a robot has at least one neighbor message waiting or a seed (corner, center, or wall) in range (an earlier version required a neighbor message, which silently discarded every seed sighting made while alone and left isolated robots permanently frozen).

Odometry here tracks position relative to the last time each kind of event occurred, not just the last decision. A robot only ever senses a single scalar per seed (signal strength, no bearing -- a real Kilobot has one IR receiver, not several), so a single "since last decision" reading loses the robot's position the moment more than one tick passes between sightings of the same kind. Instead there are two independent trackers, one anchored to the robot's last neighbor-message event and one to its last seed event, each updated by every tick regardless of which kind that tick's own event was, and each reset to zero only when its own kind fires. The update is genuine incremental dead reckoning, not the single-arc formula used for a single interval: each tick's local chord displacement is rotated by the heading accumulated since the tracker's anchor before being added to a running position, and read out by rotating that running position into the robot's current heading, so what the network receives is directly usable -- distance and bearing back to the anchor as they look from where the robot is now, not a raw offset in some frame from several ticks ago. Each tracker contributes four values (distance, sine and cosine of the bearing back to its anchor, and elapsed time since that anchor), eight in total. Elapsed time is included per tracker rather than shared, since a reading anchored two ticks ago is far more trustworthy than one anchored forty ticks ago and the network has no other way to know how stale a given reading is.

### The pose belief tracker (`python/belief.py`)

On top of the two anchored trackers, the trainer maintains a per-robot particle filter over absolute pose (x, y, theta) in the arena frame and appends its eleven-value read-out, plus three further target-relative values, to the split actor's proprioception (`SPLIT_ODOM_SIZE` = 8 + 11 + 3 = 22; see "Key shapes and constants" below). The filter is engineered, not learned: it adds zero actor parameters (the budget and the actor's real size are in "Key shapes and constants" below) and consumes only physically available signals. Its predict step applies the executed motor command's displacement and heading change per decision tick, using kinematics DERIVED from Unity's own constants rather than fitted (`prop_max_speed` 4.0, `prop_wheelbase` 4/pi, `dt_fixed` 0.02 -- see `config.py`, which computes them from moveSpeed, turnSpeed, framesPerStep and the Fixed Timestep, and `tools/check_dead_reckoning.py`, which verifies the result against a live player). The motion is modelled as the polygon the simulator actually walks, not a smooth arc, in each particle's own frame with motion-proportional noise. Its update step inverts seed strength `s = 1/(1+d)` into a range against the corner-seed table selected by `KILOBOT_SEED_LAYOUT`, and separately fuses wall-seed strength as a one-axis band constraint rather than a point range (see "Wall seeds" below -- the center-cluster seed this used to also fuse through the identical mechanism was removed from the Python side in phase 104). Resampling is gated on effective sample size so genuinely ambiguous posteriors (one beacon leaves pose free up to rotation and reflection; two leave a mirror pair) stay spread instead of collapsing to a confidently wrong mode; a spread cloud meeting a corner beacon keeps its top-weight half deterministically and gets ring hypotheses injected into the bottom half (a wall contact gets the analogous band-shaped injection); and every resample carries heading jitter unless `oracle_known_start_heading` is set, in which case heading noise is exactly zero throughout (phase 79) -- see phase 79's own entry in `docs/tuning.md` for why this changed from a small nonzero value.

A wall reading's one-axis-only limitation above is no longer absolute: when the specific nearest wall seed's own known position is available (`wall_seed_xy`, gated behind `oracle_wall_seed_position`, off the shared observation channel entirely to avoid an ml-agents shape mismatch with real Unity), a second likelihood term constrains the along-wall axis too -- the one thing a plain, identity-free wall strength reading could never provide, and specifically what lets a wrong heading hypothesis finally get discriminated against rather than surviving indefinitely. A related mechanism, off by default and evidenced to need more validation before it's ready for general use (see `config.py`'s own comment on `oracle_arrived_claim_injection`), lets a nearby, confidence-gated arrived robot's broadcast position rescue a genuinely lost neighbor's cloud through the same kind of ring injection a corner beacon gets.

The eleven read-out values are: mean position (2), heading unit vector (2), position confidence `exp(-var/0.02)` (1), heading resultant length (1), bearing and distance to the nearest seed (3), and per-axis position confidence `exp(-var_x/0.02)`/`exp(-var_y/0.02)` (2). The last two split the isotropic position confidence into its x and y components (their sum is numerically identical to the combined confidence, so nothing about the existing reward bonus changes), so the actor can act on a fix that is confident along one axis and still uncertain along the other -- exactly the state a wall contact alone produces. The bearing/distance-to-nearest-seed and the two original confidences remain the coordinates that stay observable while absolute pose is not, so the actor can steer relative to an anchor long before the cloud collapses. State lives in `worker.belief` per arena and per robot, cleared on arena reset.

### Wall seeds


The landmark table (`KILOBOT_SEED_LAYOUT`) covers a small fraction of the arena; most robots never range one within an episode, so most of the swarm has no anchor to steer by. Wall seeds close that gap by a different mechanism than the landmark table: seed robots line all four walls, spaced `WALL_SPACING` apart (26 per side at the current spacing of 8 raw units over a 200-unit wall) so no point on any wall is farther than `IR_RANGE` from the nearest one, and each broadcasts only a coarse per-side identity (which wall, not a precise position) rather than being one more entry in the landmark table. A landmark seed constrains a full 2D range against a known point; a wall seed constrains only the coordinate perpendicular to that wall, against the interior side of it (there is no rotation/reflection ambiguity to preserve here, unlike a point beacon, because the arena interior is always on a known side of any given wall). A robot at a corner is geometrically in range of two adjacent wall sides at once, but a real Kilobot has one IR receiver: it hears one of them, not both, on any given tick (fixed in phase 10, see docs/tuning.md; this section previously described the two sides as firing together, which matched the code at the time but not the hardware). `sample_split_event` narrows within the wall category the same way it already narrowed within the neighbor set, so `W_d` carries at most one nonzero side per tick, same as `S_d` carries at most one nonzero landmark. A corner still constrains both axes eventually, just never in a single tick -- it takes two separate contacts, one per side, on two different ticks.


A cold particle cloud's first wall contact needs the same kind of injection a first landmark contact does, for a related but different reason: a uniform cloud drawn within the spawn radius has near-zero density anywhere near the true wall, so plain resampling cannot manufacture a better candidate than what little the initial draw happened to include, and converges to a nearby-but-wrong value with misleadingly high confidence rather than the correct one. The fix is a band-shaped injection -- the constrained axis set near the measured value, the free axis left at each particle's own current value rather than redrawn, so that an axis fixed by an earlier tick's own injection survives a later tick's injection on the other axis instead of being overwritten by it -- gated off whenever a landmark seed also fired that tick, since the landmark's ring injection is strictly more informative when both are available. The gate deciding *whether* to inject was originally a single combined measure across both axes (`_spread`, phase 10), which meant one axis locking in tight could pull the combined value under threshold and silently stop injection for the other axis before it was ever separately measured -- confirmed empirically in a real training run, not just suspected: `belief/mean_conf_x` and `mean_conf_y` climbed at a real, practical pace while `belief/mean_conf_pos` (needing both together) climbed 6-10x slower. Phase 12 (`docs/tuning.md`) made the gate per-axis: each axis's own individual spread (not the combined one) decides whether that specific axis still needs injection, so a confident X no longer has any say over whether Y keeps receiving fresh hypotheses. Measured on the replica: roughly 79% of robots at a corner with persistent, equal-strength signal on both sides now reach both axes confident, up from 40-45% after phase 10 alone and roughly 5% before either fix.

`KILOBOT_BELIEF_COMMS` (default off) additionally commandeers message floats 0-2 as a broadcast beacon (estimated x, y, and confidence) and lets receivers range off confident senders. This is retained as an experimental channel with hard safety limits (single best sender per update, sender-sigma inflation, anchor gate 0.85, and a spread floor that structurally prevents peer-derived confidence from minting new anchors), but it is off by default: three progressively disciplined variants all degraded accuracy on the replica because independent per-robot filters exchanging mutual ranges double-count correlated information; the measured mechanisms and the path to doing it properly (covariance intersection, correlation tracking, or hop-count trust) are in the tuning log. When enabled, note that the beacon overwrites executed message floats 0-2 while PPO's stored log-probabilities cover the sampled floats, adding mean-zero gradient noise on those dims.

`Tc` and the odometry/belief proprioception are concatenated and passed through a small upscaling MLP into a GRU, which carries the robot's hidden state across ticks the same way the recurrent actor does. There is no image branch: the GRU's output goes straight into the policy head MLP with nothing concatenated onto it. Once a robot's assigned target point is resolved, `simple_oracle.py`'s navigating-phase steering never references the target image again, so the target-relative bearing/distance values already inside the proprioception (see "Key shapes and constants" below) are a sufficient replacement for what a compressed image feature could have provided. The policy head produces the same eleven-value squashed-Gaussian mean as the other two actors, plus an optional twelfth "arrived" logit when `use_arrived_head` is set (phase 142) -- a separate, trained flag that, once confident, forces the motor to zero and freezes the GRU's own hidden state, rather than relying on the continuous motor head alone to learn "stop and sit here." All of the hidden widths (the upscaling MLP, the GRU, the policy head) are configurable; see "Key shapes and constants" below for the actor's own current, real size and budget, not a fixed parameter count -- both have changed more than once since this was first written.

## The critic

The critic is a graph attention network (GATv2). Its input is the whole arena as a graph for a single timestep: one node per robot with that robot's features, and edges between robots that are within communication range. Attention lets it weigh neighbors differently when forming each robot's representation. It pools the arena into a value estimate.

Because arenas have different numbers of robots and edges, the per-arena graphs are concatenated into one big batched graph before the critic runs over them. `graph_batch.py` does that packing.

## The target image

A shape is given as a small image. A pretrained encoder (`image_encoder.pt`, loaded by `encoder.py`) turns that image into a latent vector of length 64. That latent is given to both the actor and the critic so they know which shape is the goal. The encoder is frozen during reinforcement learning; only the actor and critic train.

## The training loop

One iteration looks like this.

1. Collect a rollout. For a fixed number of steps, Python reads observations from every arena, the actor chooses actions for every robot, those actions go back to Unity, and Unity advances the physics. Robots decide every few simulation frames rather than every frame, which is a standard frame-skip. On each decision step the side channel delivers each arena's graph, which is stored for the critic.

2. Compute returns and advantages. The critic scores the stored graphs, and generalized advantage estimation (`gae.py`) turns the rewards and values into training targets.

3. Update. PPO (`ppo.py`) updates the actor with the clipped policy objective and the critic with a value-regression loss, over several passes through the collected data.

4. Log and checkpoint. Metrics go to TensorBoard and the console, and a checkpoint is written periodically.

## Scripted controllers, behaviour cloning, and warm-starting

Alongside normal PPO training, the environment can be driven by a hand-written controller instead of the actor's policy (`cfg.motor_override`, via `KILOBOT_MOTOR_OVERRIDE`). This exists for two purposes: as a diagnostic ceiling (does a simple, always-available controller solve the task at all, bounding what RL could plausibly achieve), and as a teacher for behaviour cloning.

**`simple_oracle.py` is the oracle** (`motor_override="simple_oracle"`). It is a from-scratch five-state machine — `go_north` → `turning` → `wall_following` → `navigating` → `arrived`, strictly linear with no back-edges — and it uses **no privileged information**: heading is dead-reckoned from the robot's own commanded motors starting from a known spawn convention, and position is genuinely unknown until real wall or landmark contact narrows it. Targets are assigned by a decentralised hash of each robot's own index over a Hilbert ordering of the shape (`spatial_hash.py`), so no coordination or central assignment is needed. There is a second, older controller, `actor_io.scripted_motors` (`motor_override="oracle"`), which steers from the belief filter's heading estimate; it is not the BC teacher.

Two entry points clone the actor to it:

- **`run_bc_monitored.py`** — the maintained one, and what `scripts/train_bc.sh` runs. Holds out formations for validation, records a val tape (observations plus oracle targets, replayed with no simulation cost), keeps a per-oracle-state replay reservoir, and reports per-state imitation error rather than coverage alone.
- **`run_bc_simple_oracle.py`** — the minimal loop, for when you want nothing but the clone and an export.

Cloning is ordinary supervised regression against the oracle's motor output: no exploration difficulty, and cheap relative to RL. It supervises only the motor output, not the message channel — the message head receives no gradient from BC and starts RL fine-tuning as randomly initialised as it would from scratch.

Warm-starting RL from a clone needs no bridging step: `KILOBOT_INIT_ACTOR=<actor.pt> KILOBOT_MODE=rl python launch.py` loads the cloned actor's weights and starts a normal run with a fresh critic and optimizers. That lets RL spend its exploration budget on what the oracle cannot teach — coordination, and adapting to genuine localization uncertainty — rather than rediscovering basic navigation.

`scripts/watch_oracle.sh` and `scripts/watch_actor.sh` drive one visible arena with no training, for open-ended inspection: the oracle, or a trained checkpoint. Both need a separate, headed Unity build; the normal training build is a headless server build with no rendering pipeline compiled in, so pointing these at it produces no window.

## Reward

The reward is based on how well the swarm currently covers the target shape (`reward.py`). Coverage is the quantity to watch in the logs as a rough measure of progress. The exact shaping of this reward is one of the open research questions; the current shape trains stably but has not produced reliable assembly.

For the split-observation actor specifically, two small additive terms bias exploration without competing with the task itself: `belief_confidence_bonus` (localization scaffolding, meant to be annealed away over the course of a run -- but only if `belief_conf_bonus_iters` is explicitly set; it defaults to `0`, which keeps the bonus constant for the whole run instead, a real gap phase 8 (`docs/tuning.md`) found live in a real training run, now at least warned about at startup) and `seed_wall_find_reward`, a one-time nudge paid the tick after a decision was triggered by a landmark seed (positive, `seed_find_bonus`) or a wall seed (negative, `wall_find_penalty`) -- encouraging robots to seek out landmark contact specifically, since a landmark seed resolves full position while a wall seed only ever resolves one axis. Both default to a magnitude an order of magnitude below the on-shape reward, so neither can make holding still on a wrong spot more attractive than finishing the task.

## Scaling

There are two ways to run training.

Single process. One Unity instance with several arenas, with collection and the PPO update in the same process. This is the simplest path and the right one for quick checks. Set `KILOBOT_NUM_WORKERS=1`.

Multi process. Several worker processes each drive their own Unity instance and run the actor on CPU. A separate learner process gathers all of their rollouts, runs PPO, and runs the critic, and it is the one that can use a GPU. Set `KILOBOT_NUM_WORKERS` to 2 or more. Collection then happens in parallel across workers, while the heavy PPO and critic step happens once on the learner. The rollouts are packed into a handful of large tensors before they cross between processes, because sending thousands of small tensors through a queue is slow. If a worker dies during a run, the learner detects it and stops cleanly instead of hanging, keeping the latest checkpoint.

On CPU, the multi-process setup is roughly even with single process, because the PPO step is serial and grows with the amount of data. The gain shows up when the learner runs PPO and the critic on a GPU, which shrinks that serial step and lets the parallel collection pay off.

## Deployment

Only the actor is kept. `checkpoint.py` exports it on its own as `actor_final.pt`, with no dependence on the critic or the graph side channel. That export is the artifact you would put on a swarm: a single small network that every robot runs on local information.

## Key shapes and constants

These live in `kilobot_gnn.py` and `config.py`, which are the source of truth. This section has fallen out of sync with them before, so check the code directly for anything load-bearing. `tests/test_kilobot.py` pins the ones below that can be pinned:

- Target latent size: 64 (DeepSet actor only -- see below).
- Action: two motor values plus a broadcast message, eleven values in total.
- Neighbor message: nine values.
- Seed reference: four values, one per corner landmark. There is no center cluster; it was removed from both sides.
- Neighbor memory: a fixed-capacity database of recent messages per robot (DeepSet actor only).
- Split-observation actor: **eighteen-value** typed event vector `Tc` (`SPLIT_TC_SIZE`: nine-value neighbor message + one neighbor strength + four corner-seed slots + four wall-seed slots -- no center-cluster segment, removed phase 104), **twenty-two-value** proprioception (`SPLIT_ODOM_SIZE`: eight two-tracker odometry values, four per tracker, plus eleven base belief-filter values, plus three further belief-filter values giving bearing/distance to the robot's own assigned target -- phase 106; a widely-recurring error in this project's own documentation, including a draft of the user's own paper, states this as nineteen, omitting the three target-relative values entirely). **No image feature of any width** -- the online-compressed image branch this section used to describe here was removed entirely in phase 106; `belief_read`'s own target-relative bearing/distance, already counted in the twenty-two above, is a confirmed, strictly sufficient replacement, verified directly against what `simple_oracle.py`'s own navigating-phase steering actually uses. Two further, opt-in additions since, each expanding the actor's own first-layer input width by a fixed amount only when explicitly enabled (`use_arrived_head` does not touch input width at all -- it adds an output head instead): `use_turn_anchor` (phase 146) adds two values, sin/cos of the heading change since the robot's own wall reading last went from zero to nonzero.
- Critic graph node features: nineteen values per robot (`NODE_FEATURES`).
- Frame-skip: robots decide every four simulation frames. Unlike every other value on this list, this is not sourced from `kilobot_gnn.py`/`config.py` -- it is set by ML-Agents' `DecisionRequester` component in the Unity Editor Inspector, invisible to this repository's `unity/` script mirror, and nothing on the Python side pushes a value into it.
- GAE discount 0.99, lambda 0.95, PPO clip 0.2.
- Actor parameter budget: a user-specified **24KB (24576 bytes) hard limit at int8 quantization** (phase 147, tighter than an earlier 28000-parameter figure this document and others in this project previously cited) -- the real, practical actor (`use_arrived_head=True, use_turn_anchor=True`, `split_gru_hidden=59`) measures 24129 bytes, verified directly against real layer objects and a saved checkpoint's own state_dict, not assumed.
